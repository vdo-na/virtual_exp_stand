В качестве целевой системы выбран стек Shlink — готовая, промышленная open-source система сокращения ссылок и аналитики с микросервисной архитектурой.

Компоненты системы:

СУБД (База данных): postgres:16-alpine — реляционная СУБД для хранения зарегистрированных ссылок, тегов, метаданных посещений и API-токенов.

Серверная часть (API-бэкенд): shlinkio/shlink:stable — серверное приложение на базе PHP 8 / RoadRunner (высокопроизводительный сервер приложений на Go). Предоставляет REST API и обрабатывает редиректы. Является полностью stateless, благодаря чему легко масштабируется горизонтально.

Клиентская часть (Фронтенд): shlinkio/shlink-web-client:stable — отдельное клиентское Single Page Application (SPA) на React, раздаваемое легковесным веб-сервером Nginx.

## 6. Описание выбранного балансировщика и метода балансировки

* **Балансировщик нагрузки:** **Traefik v3.1** — современный реверс-прокси и L7-балансировщик, ориентированный на облачные среды и контейнеры.
* **Механизм интеграции:** Traefik подключается к сокету Docker (`/var/run/docker.sock`) и в режиме реального времени отслеживает жизненный цикл контейнеров, динамически регистрируя их адреса без необходимости ручной перезагрузки конфигурации.
* **Метод балансировки:** **Round-Robin (циклический перебор)**.
  Запросы, поступающие на роутеры `shlink_api_1` и `shlink_api_2`, направляются в единый пул `shlink_backend`. Внутренний механизм Traefik распределяет поступающие TCP/HTTP соединения строго по очереди между `shlink_backend_1` и `shlink_backend_2`.

## 8. Трудности, возникшие в ходе работы, и найденные решения

В процессе проектирования, развертывания и функциональной верификации виртуального экспериментального стенда был выявлен и решен ряд практических проблем:

1. **Коллизия сетевых портов при горизонтальном масштабировании (`listen tcp 0.0.0.0:8081: bind: Only one usage of each socket address`):**
   * *Причина:* При попытке масштабировать бэкенд стандартной директивой `deploy.replicas: 2` с указанием диапазона портов `8081-8082:8080` Docker Compose в standalone-режиме под управлением Windows попытался назначить первый порт диапазона (`8081`) обоим запускаемым контейнерам одновременно. Дополнительно порт 8081 периодически блокировался внутренними службами хостовой операционной системы.
   * *Решение:* Серверная часть в конфигурации `docker-compose.yml` была явно разделена на два независимых сервиса (`backend1` и `backend2`) с жесткой привязкой свободных статических портов `9081` и `9082`. На уровне балансировщика Traefik обе ноды были объединены в единый балансировочный пул с помощью общего лейбла `traefik.http.services.shlink_backend.loadbalancer.server.port=8080`.

2. **Аварийное завершение контейнеров бэкенда при холодном старте (Exit 137 / OOM-Killed):**
   * *Причина:* Первоначально заданный лимит оперативной памяти `256M` приводил к принудительному завершению PHP-процессов ядром Linux (Out-Of-Memory Killer). Во время первого запуска бэкенд накатывал миграции схемы базы данных через Doctrine ORM, что кратковременно требовало до 320–350 МБ RAM.
   * *Решение:* Аппаратный лимит памяти для сервисов бэкенда был скорректирован до `512M`. Дополнительно для контейнера СУБД PostgreSQL был настроен блок `healthcheck`, а для бэкенда добавлено условие `condition: service_healthy`, предотвращающее запуск API до полной готовности базы данных к приему TCP-соединений.

3. **Конфликт маршрутов Traefik и вызов некорректного эндпоинта (HTTP 404 «Oops! We could not find requested route»):**
   * *Причина 1:* Дублирование одинаковых имен роутеров у обоих сервисов бэкенда приводило к коллизии внутри Traefik и отбрасыванию роутера API в пользу более общего роутера фронтенда.
   * *Причина 2:* Проверка работоспособности по ошибке выполнялась по несуществующему в спецификации Shlink URL `/rest/v3/health`. 
   * *Решение:* Роутеры бэкендов были разделены по именам (`shlink_api_1` и `shlink_api_2`), их приоритет маршрутизации был повышен до максимального (`priority=100`), а запросы проверки перенаправлены на документированный системный эндпоинт `/rest/health`.

4. **Ложный перехват трафика фронтендом и скрытое клиентское кеширование через Service Worker (PWA):**
   * *Причина:* Первоначальное использование общего правила `PathPrefix('/')` для фронтенда без явной фильтрации по домену привело к тому, что домен `api.localhost` был ошибочно перехвачен веб-клиентом. Так как Shlink Web Client является **Progressive Web Application (PWA)**, браузер зарегистрировал в своей памяти фоновый скрипт **Service Worker** для домена `api.localhost`. В дальнейшем, даже после полного исправления правил маршрутизации в Traefik (`Host('api.localhost')` для бэкенда и `Host('localhost')` для фронтенда), браузер в стандартном режиме **вообще не отправлял сетевой HTTP-запрос в Traefik/Docker**. Service Worker перехватывал обращение к `http://api.localhost/xxxxxx` локально внутри браузера, отдавал сохраненный на диске React-клиент, а внутренний React Router, не найдя указанный путь, генерировал собственную 404-страницу («Oops»).
   * *Решение:* 
     * Проблема была локализована путем изолированной проверки сетевого стека через утилиту `curl` и открытие сессии в режиме инкогнито (Private Browsing), где Service Worker и дисковый кеш принудительно отключаются — в этом случае сервер мгновенно возвращал ожидаемый ответ `HTTP 302 Found` с редиректом на целевой ресурс (Google).
     * В основном браузере была выполнена очистка рабочего окружения через Chrome DevTools (*F12 -> Application -> Service Workers -> Unregister*, а также *Storage -> Clear site data*).
     * В файле `docker-compose.yml` было окончательно зафиксировано строгое разграничение по доменным именам: фронтенд слушает исключительно `Host('localhost')`, а бэкенд — `Host('api.localhost')`.

## 9. Ответы на контрольные вопросы

### 1. Какую роль выполняет балансировщик нагрузки?
Балансировщик нагрузки (Load Balancer) выполняет следующие ключевые функции:
* **Распределение трафика:** Равномерно распределяет поступающие клиентские сетевые/HTTP-запросы между пулом вычислительных узлов, предотвращая перегрузку отдельных серверов.
* **Обеспечение отказоустойчивости (High Availability):** Непрерывно выполняет проверки жизнеспособности (health checks) узлов и автоматически исключает сбойные инстансы из маршрутизации.
* **Масштабируемость:** Позволяет прозрачно для конечного пользователя добавлять или выводить вычислительные мощности из пула.
* **Терминирование SSL/TLS и безопасность:** Снимает с бэкендов накладные расходы на шифрование трафика и защищает инфраструктуру от всплесков нагрузки и DoS-атак.

### 2. Какое программное обеспечение может использоваться в качестве балансировщика?
* **Специализированные обратные прокси / балансировщики:** Traefik, Nginx, HAProxy, Envoy, Caddy.
* **L4-балансировщики ядра Linux:** IPVS (IP Virtual Server), Keepalived.
* **Облачные балансировщики:** AWS Application Load Balancer (ALB), Cloudflare Load Balancing, Yandex Network Load Balancer.
* **Аппаратно-программные комплексы:** F5 BIG-IP, Citrix ADC.

### 3. Как внести ограничения на объем используемых ресурсов в Docker?
* **В файле `docker-compose.yml` (через подсистему Linux cgroups):**
  С помощью директивы `resources.limits`:
  ```yaml
  deploy:
    resources:
      limits:
        cpus: '0.5'        # Ограничение 50% времени одного ядра CPU
        memory: 256M       # Лимит оперативной памяти (при превышении — OOM Kill)
  ```
* **Через CLI (`docker run`):**
  * Память: `--memory="256m"`, `--memory-swap="512m"`.
  * Процессор: `--cpus="0.5"`, `--cpu-shares=512`.
* **Ограничение пропускной способности сети:**
  * На уровне контейнера: с помощью встроенного механизма ядра Linux Traffic Control (`tc`) внутри контейнера с привилегией `NET_ADMIN`.
  * На уровне гипервизора (VirtualBox): через консоль управления полосой адаптера: `VBoxManage bandwidthctl "VM" add Limit --type network --limit 10M`.

### 4. Что такое горизонтальное масштабирование?
**Горизонтальное масштабирование (Scale-Out)** — это метод повышения производительности и надежности системы за счет увеличения **количества** параллельно работающих независимых узлов (серверов, контейнеров), объединенных балансировщиком нагрузки. 

В отличие от *вертикального масштабирования (Scale-Up)*, при котором увеличивается аппаратная мощность одного сервера (добавление ядер CPU или планок RAM), горизонтальное масштабирование практически не имеет физического потолка и обеспечивает высокую отказоустойчивость: падение одной ноды не приводит к отказу всей системы.

### 5. Какие методы (алгоритмы) для балансировки нагрузки существуют?
1. **Round Robin (Циклический перебор):** Запросы распределяются по очереди по кругу. Подходит для пула узлов с одинаковой производительностью.
2. **Weighted Round Robin (Взвешенный циклический):** Серверам назначаются весовые коэффициенты. Более мощные серверы получают пропорционально большее число запросов.
3. **Least Connections (Минимум соединений):** Запрос направляется серверу, у которого в данный момент меньше всего активных клиентских сессий. Эффективно для длительных транзакций.
4. **IP Hash / Source IP:** Сервер выбирается на основе хеш-функции от IP-адреса клиента. Гарантирует попадание одного и того же клиента на один и тот же бэкенд (Sticky Sessions).
5. **Least Response Time (Минимальное время отклика):** Трафик отдается серверу, который быстрее всего ответил на контрольный запрос и имеет наименьшее число соединений.
