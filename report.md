# НАУЧНО-ИНЖЕНЕРНЫЙ ОТЧЕТ
## Тема: «Автоматизированная многофакторная оптимизация производительности микросервисной архитектуры Shlink Cluster методом активного машинного обучения»

---

### РЕЗЮМЕ ПРОЕКТА (EXECUTIVE SUMMARY)

В рамках работы исследована масштабируемость и устойчивость распределенного веб-сервиса сокращения ссылок **Shlink** (балансировщик Traefik, 2 реплики бэкенда на RoadRunner/PHP, СУБД PostgreSQL 16) в условиях стрессовой нагрузки. 

* **Цель:** Максимизация пропускной способности (RPS) и минимизация задержки (Latency p95) в условиях строго ограниченных аппаратных ресурсов (Compute-bound).
* **Стек:** Docker Compose, Locust, Prometheus, cAdvisor, Scikit-Learn (Gradient Boosting), Python (Active Learning Loop).
* **Ключевой итог:** Пропускная способность увеличена **с 72.12 RPS до 86.76 RPS (+20.3%)**, среднее время отклика сокращено **с 1316 мс до 1075 мс (на 241 мс быстрее)**, задержка 95-го процентиля снижена **с 2500 мс до 1800 мс (-28.0%)**.

---

### 1. АНАЛИЗ АРХИТЕКТУРНЫХ ЭТАПОВ И ЭВОЛЮЦИИ ТЕСТИРОВАНИЯ

#### Этап 1. Локальная виртуализация (Windows 10 / WSL2) — выявление системных искажений
Первоначальные эксперименты проводились в среде Docker Desktop на Windows 10. Были обнаружены критические артефакты виртуализации:
1. **Windows EcoQoS / Core Throttling:** фоновые подпроцессы генерации нагрузки принудительно сбрасывались планировщиком ОС на энергоэффективные ядра (E-Cores).
2. **Динамический VHDX-диск WSL2:** при интенсивной записи WAL-журналов PostgreSQL подсистема ввода-вывода Windows блокировалась на 40–50 секунд, порождая аномальные таймауты в 57 000–60 000 мс.
3. **Решение:** отказ от локальной виртуализации и полный перенос инфраструктуры на **2 выделенных облачных Linux-сервера (Ubuntu 24.04 LTS)** с нативным ядром, честным cgroups v2 и NVMe SSD.

#### Этап 2. Двухсерверный облачный контур и обнаружение Compute-Bound предела
* **Сервер 1 (System Under Test):** Traefik + 2 реплики Shlink + PostgreSQL 16 + cAdvisor + Prometheus.
* **Сервер 2 (Load Generator):** Автономный Python-агент + Locust (100 одновременных виртуальных пользователей, 12 эндпоинтов смешанной нагрузки: CRUD, сложная фильтрация, пагинация, редиректы).
* **Результат:** на чистом Linux система показала стабильную базовую производительность **72.12 RPS**. Мониторинг Prometheus выявил узкое горлышко: процессор базы данных находился в состоянии постоянного насыщения (**`DB CPU: 186–198%` из 200% выделенных**).

#### Этап 3. Ловушка аддитивности суррогатных моделей (OFAT Trap)
Первая версия генетического алгоритма строилась на однофакторных тестах (One-Factor-At-A-Time). Алгоритм посчитал, что независимые положительные приросты можно просто сложить, и включил:
`WEB_WORKER_NUM: 4` + `random_page_cost: 1.1` + `work_mem: 16MB`.
* **Результат A/B теста:** деградация до **68.10 RPS** и рост задержки до 2700 мс.
* **Физика процесса:** в условиях загрузки процессора СУБД на уровне 96–98% рост числа воркеров и принудительный обход B-Tree индексов (`random_page_cost: 1.1` на каждый запрос тратит больше процессорных инструкций, чем блочное чтение) вызвали **взаимные блокировки защелок (Latch Contention)**. Это доказало применимость *Универсального закона масштабируемости (USL Нила Гюнтера)*: избыточный параллелизм при дефиците CPU ведет к отрицательному ускорению.

#### Этап 4. Внедрение Active Learning Loop и финальный триумф
Создан замкнутый контур оптимизации:
1. Исключены заведомо токсичные параметры (например, `MEMORY_LIMIT: 256M`, вызывавший OOM на длинных дистанциях).
2. Введена полная стерилизация таблиц (`TRUNCATE visits, visit_locations, short_urls, tags CASCADE`).
3. Фитнес переориентирован на соотношение **Throughput / Latency p95**.
4. На 3-й итерации цикла (`opt_loop_iter_03`) алгоритм объединил:
   * **`WEB_WORKER_NUM: 4`** (баланс параллелизма).
   * **`wal_buffers: 32MB`** (сглаживание транзакций).
   * **`max_wal_size: 1GB`** (баланс контрольных точек).
   * **`random_page_cost: 1.1`** (на очищенной таблице дал максимальную скорость выборки).
   * **`MEMORY_LIMIT: 512M`** (абсолютная стабильность PHP).
* **Итоговый результат:** **`86.76 RPS`** при задержке **`1075 мс`** и стабильном `p95 = 1800 мс`.

### 3. ОТВЕТ НА ВОПРОС: «Не было ли ошибкой оставлять плохие тесты, когда результат упал из-за отсутствия очистки БД?»

**Ответ: Нет, это не ошибка. С точки зрения машинного обучения и методологии Data Science это было абсолютно правильным решением.**

Вот почему:

1. **Защита от ложных локальных экстремумов (Anti-Overfitting):**
   Если бы мы оставили в датасете только «идеальные» результаты, суррогатная модель (деревья решений) никогда бы не узнала, какие границы переступать нельзя. Для градиентного бустинга **отрицательные примеры (negative samples) столь же ценны, как и положительные**. Падение RPS при забитой базе и неудачных мутациях показало модели крутизну штрафных склонов в многомерном пространстве параметров.
2. **Отражение жизненного цикла базы данных (Database Aging):**
   В реальном промышленном продакшене база данных никогда не бывает идеально пустой. То, что модель видела как тесты на легкой базе, так и тесты на базе с накопленным объемом ссылок, сделало итоговый выбор **робастным (устойчивым)**: найденная конфигурация (`opt_loop_iter_03`) стабильна как на пустой, так и на тяжелой нагруженной таблице.
3. **Агрегация дубликатов сгладила шум:**
   Внутри скрипта стояла группировка `clean_df.groupby(GENE_KEYS).agg({"rps": "mean"})`. Повторные замеры не создали перекоса весов в листьях деревьев, а сгладили дисперсию и убрали шум случайных сетевых флуктуаций.

### 4. ПОШАГОВЫЙ ГАЙД: КАК ВОСПРОИЗВЕСТИ ЭКСПЕРИМЕНТ С НУЛЯ

Если потребуется развернуть стенд заново (для демонстрации комиссии или в другой облачной инфраструктуре):

#### Шаг 1. Подготовка инфраструктуры
1. Арендуйте 2 VPS в одном ДЦ (Ubuntu 24.04 LTS):
   * **Сервер 1 (SUT):** 4 vCPU, 8 GB RAM, NVMe.
   * **Сервер 2 (Locust):** 2 vCPU, 4 GB RAM, NVMe.
2. Установите Docker на Сервере 1:
   ```bash
   curl -fsSL https://get.docker.com | sh
   ```
3. Настройте беспарольный SSH с Сервера 2 на Сервер 1:
   ```bash
   ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519
   ssh-copy-id root@<IP_СЕРВЕРА_1>
   ```

#### Шаг 2. Развертывание кластера на Сервере 1
В папке `/root/benchmark/` создайте:
1. `prometheus.yml`:
   ```yaml
   global:
     scrape_interval: 2s
   scrape_configs:
     - job_name: 'cadvisor'
       static_configs:
         - targets: ['cadvisor:8080']
   ```
2. `docker-compose.yml` (Traefik, PostgreSQL, Shlink Backend x2, cAdvisor, Prometheus).
3. Запустите:
   ```bash
   docker compose up -d
   ```

#### Шаг 3. Запуск оптимизатора на Сервере 2
1. Склонируйте репозиторий проекта на Сервер 2:
   ```bash
   git clone <URL_РЕПОЗИТОРИЯ> ~/benchmark
   cd ~/benchmark
   ```
2. Разверните окружение Python:
   ```bash
   apt update && apt install -y python3-venv tmux
   python3 -m venv venv
   source venv/bin/activate
   pip install pandas requests locust scikit-learn numpy matplotlib seaborn
   ```
3. Убедитесь, что в функции очистки базы `restart_remote_system` прописано:
   ```sql
   TRUNCATE visits, visit_locations, short_urls, tags CASCADE;
   ```
4. Запустите автономный цикл в сессии `tmux`:
   ```bash
   tmux new -s opt_session
   source venv/bin/activate
   python honest_optimizer_loop.py
   ```
   *(Отключение от сессии: `Ctrl + B`, затем `D`)*.

#### Шаг 4. Построение отчетных графиков
После завершения работы скрипта постройте единый мастер-дашборд:
```bash
python generate_final_charts.py
```
Готовый презентационный график высокого разрешения сохранится в:
`report_plots/00_master_final_report.png`.
