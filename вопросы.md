### 6. Описание используемых сценариев нагрузочного тестирования

Нагрузочное тестирование реализовано с использованием фреймворка **Locust** в двухсерверной конфигурации (генератор нагрузки изолирован от целевого кластера, задержка сети между серверами $< 1$ мс). 

Профиль нагрузки моделирует смешанный пользовательский поток распределенного сервиса сокращения ссылок, разделенный на три параллельные поведенческие роли с заданными вероятностными весами:

1. **Обычный пользователь (Regular Visitor)** — вес **70%** (7/10 трафика):
   * `GET /{shortCode}` — переход по существующей короткой ссылке (проверка выдачи HTTP 302/307 Redirect, регистрация визита в СУБД, определение геолокации по IP через эмулированный заголовок `X-Forwarded-For`).
   * `GET /{invalidCode}` — обращение к несуществующему коду (проверка обработки HTTP 404 и записи orphan-визитов).
   * Интенсивность: минимальные интервалы ожидания (`wait_time = between(0.01, 0.05)` с), генерирующие агрессивный поток транзакций.

2. **Администратор (Admin User)** — вес **10%** (1/10 трафика):
   * `POST /rest/v3/short-urls` — создание новых коротких ссылок с тегами и метаданными (транзакционная запись в таблицы `short_urls`, `tags`).
   * `PATCH /rest/v3/short-urls/{shortCode}` — обновление метаданных ссылки и смена тегов (операции `UPDATE` в СУБД).
   * `GET /rest/v3/short-urls` — сложный поиск по подстроке, фильтрация по тегам и сортировка по количеству переходов (`orderBy[visits]=DESC`, генерация нагрузки на индексы и строковые фильтры).
   * `GET /rest/v3/tags` — получение справочника тегов.
   * `DELETE /rest/v3/short-urls/{shortCode}` — удаление ссылки (срабатывает контролируемо, поддерживая размер пула).

3. **Статистик / Аналитик (Statistician User)** — вес **20%** (2/10 трафика):
   * `GET /rest/v3/short-urls/{shortCode}/visits` — получение пагинированного списка кликов конкретной ссылки.
   * `GET /rest/v3/tags/{tag}/visits` — агрегация статистики просмотров по рекламным тегам.
   * `GET /rest/v3/visits/orphan` — выгрузка статистики 404-трафика.
   * `GET /rest/v3/visits/non-orphan` — ресурсоемкий аналитический запрос выборки визитов за 24 часа с исключением бот-трафика (`startDate=...&excludeBots=true`, тяжелые `JOIN` и фильтрация по диапазонам времени).
   * `GET /rest/v3/tags/stats` — сводная статистика по тегам.

**Параметры масштабирования теста:**
* Количество одновременных виртуальных пользователей ($U$): **100**.
* Скорость разгона (Spawn rate): **20 пользователей в секунду** (выход на стационарный режим за 5 секунд).
* Длительность зачетных испытаний: **10 минут (600 с)** и **25 минут (1500 с)** для исключения влияния переходных процессов и прогрева кэшей.

### 7. Перечисление критериев эффективности

Оценка качества функционирования системы производилась по комплексу метрик производительности, надежности и утилизации аппаратных ресурсов:

1. **Метрики производительности (Throughput & Latency):**
   * **$RPS$ (Requests Per Second)** — среднее количество успешно обслуженных HTTP-запросов в секунду (главный максимизируемый показатель).
   * **$T_{avg}$ (Average Latency)** — среднее время отклика системы на запрос, мс.
   * **$T_{p95}$ (95th Percentile Latency)** — задержка 95-го процентиля: время, в которое укладывается 95% всех обработанных запросов, мс (показатель стабильности хвоста распределения).

2. **Метрики надежности:**
   * **$FailRatio$ (%)** — процент сбойных запросов (HTTP 5xx, таймауты сокетов):
     $$FailRatio = \frac{N_{failed}}{N_{total}} \times 100\%$$
     Критерий применимости конфигурации: $FailRatio \le 0.1\%$.

3. **Метрики утилизации ресурсов (Prometheus / cAdvisor):**
   * **$CPU_{db}^{max}$ (%)** — пиковая загрузка процессора контейнера СУБД PostgreSQL (2 ядра = 200%).
   * **$CPU_{backend}^{max}$ (%)** — пиковая загрузка процессора контейнеров бэкенда Shlink.
   * **$RAM_{backend}^{max}$ (MB)** — пиковое потребление оперативной памяти пулом PHP-воркеров RoadRunner.

4. **Интегральный критерий эффективности (Целевая функция приспособленности / Fitness Score):**
   Для многокритериальной оптимизации использована целевая функция, поощряющая высокую пропускную способность, штрафующая за рост задержек выше порога SLA и накладывающая барьер на деградацию:
   $$\Phi(C) = \begin{cases} 
   \dfrac{RPS}{\log_{10}(T_{p95}) + 0.1} \cdot (1 - FailRatio), & \text{при } T_{p95} \le 4000\text{ мс} \\ 
   \dfrac{RPS}{\log_{10}(T_{p95}) + 0.1} - \gamma \cdot (T_{p95} - 4000), & \text{при } T_{p95} > 4000\text{ мс} 
   \end{cases}$$
   где $\gamma$ — штрафной коэффициент за деградацию времени отклика.

### 9. Описание используемых методов

Для решения задачи нахождения оптимального вектора параметров $C^* = \arg\max \Phi(C)$ в дискретном пространстве размерности $N = 10\,368$ вариантов использован комплекс взаимосвязанных методов:

1. **Метод пофакторного анализа (One-Factor-At-A-Time, OFAT):**
   Первичный сбор обучающей выборки путем варьирования каждого параметра в отдельности относительно базового профиля. Метод позволил выявить локальные экстремумы отдельных факторов (например, деградацию при `WEB_WORKER_NUM > 4` и оптимум `max_wal_size`).

2. **Моделирование с разной степенью детализации (Multi-Fidelity Modeling):**
   Объединение в единую выборку разнородных экспериментов разной продолжительности:
   * Low-fidelity: быстрые 2-минутные прогоны (120 с, вес выборки $w = 1.0$) — выявление формы отклика.
   * Mid-fidelity: 5-минутные прогоны (300 с, вес $w = 1.5$).
   * High-fidelity: 25-минутные Soak-тесты (1500 с, вес $w = 3.0$) — учет долговременных эффектов накопления индексов и чекпоинтов.
   Обучение велось с весами объектов (`sample_weight`), что позволило расширить обучающую выборку до 50+ точек без потери точности на стационарном режиме.

3. **Суррогатное моделирование (Surrogate Modeling):**
   Аппроксимация неизвестной целевой функции $\Phi(C)$ ансамблем решающих деревьев — градиентным бустингом **`GradientBoostingRegressor`** (`n_estimators=100`, `max_depth=3`). Алгоритм строит нелинейную поверхность функции отклика по категориальным признакам, закодированным через `OneHotEncoder`.

4. **Генетический алгоритм (Genetic Algorithm, GA):**
   Поиск глобального оптимума на обученной суррогатной поверхности:
   * *Хромосома:* вектор из 9 дискретных генов.
   * *Популяция:* 80 особей, 50–60 поколений.
   * *Операторы:* элитизм (сохранение топ-10% лучших решений), турнирная селекция, равномерный кроссовер (Uniform Crossover с вероятностью $p_c = 0.5$), точечная мутация генов ($p_m = 0.15–0.20$).
   * *Механизм защиты от повторов:* отсев конфигураций, уже зафиксированных в истории замеров, с принудительной мутацией в неисследованные области.

5. **Автономный замкнутый цикл оптимизации (Active Learning Loop):**
   Итеративный процесс без участия оператора:
   $$\text{Данные} \rightarrow \text{Обучение суррогата} \rightarrow \text{Генетический поиск кандидата} \rightarrow \text{SSH-деплой} \rightarrow \text{Реальный тест} \rightarrow \text{Анализ} \rightarrow \dots$$
   *Условие останова (Early Stopping):* алгоритм завершает работу при отсутствии статистически значимого прироста ($\Delta RPS < 0.3$) на протяжении $P$ последовательных итераций (`Patience = 4`), фиксируя достижение сходимости.

6. **Контрольная онлайн-валидация (A/B Testing):**
   Обязательное контрольное 25-минутное сравнение найденного «чемпиона» с исходной базовой конфигурацией в идентичных внешних условиях для верификации предсказаний модели.
